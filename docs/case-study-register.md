# Recommendation 문제 해결 사례 기록

## 선정 기준과 현재 상태

최종 README는 독립적인 실제 문제 해결 사례 **정확히 4개**를 유지한다. 채용 검토에서 기술적 판단을 설명할 수 있는 문제의 영향, 원인을 좁힌 증거, 대안, 실제 구현과 결과를 우선한다. 새 사례의 근거가 더 강하면 기존 사례와 비교한 이유를 남기고 즉시 교체한다.

현재 HTTP 계약은 `GET /health`·학습하지 않은 `POST /v1/recommendations/baseline`과 요청 카탈로그의 `POST /v1/recommendations/content`다. B1 HTTP는 허구 입력으로 연결·요청 상태 격리를 검증했고 서비스 카탈로그 학습·품질 평가·Backend B1 연동은 미완료다. 근거가 있는 독립 사례는 **2개**, 추가 확보가 필요한 사례는 **2개**다. 패키징·lockfile·CI를 각각 별개의 문제 해결로 나눠 네 개를 맞추지 않았다. 아래 미완료 항목은 후보 과제이며 README의 구현 성과가 아니다.

| ID | 주제 | 상태 | README 반영 |
|---|---|---|---|
| REC-CS05 | HTTP200의 원천 오류와 수집 완료·상품 부재를 분리 | 실제 maxlag·receipt/revision·실패 거절 근거 확보 | REC-CS01을 교체 |
| REC-CS02 | B0의 필수 조건·unknown·결정적 순서 | 현재 예방적 설계·구현 근거 확보 | 반영 |
| REC-CS03 | 신규 사용자·결측 특성·서비스 실패의 대체 추천 구분 | 미구현, 공통 API 계약·장애 재현 필요 | 미반영 |
| REC-CS04 | 공개 데이터와 서비스 카탈로그의 평가 경계·누수 방지 | 미구현, 데이터·학습·평가 기록 필요 | 미반영 |

## REC-CS05 — HTTP200 안의 오류와 카탈로그 완료 상태

- 실제 조건: 새 item 단일 GET은 HTTP200·API maxlag였고 수집기가 accepted=false/실패 종료로 보류했다. 초기 probe의 get(search,[])는 같은 원천 오류를 빈 결과처럼 표시할 위험을 보여 원문으로 정정했다. 실제 서비스의 과거 장애 수정으로 표현하지 않는다.
- 구현: [수집기](../src/pubburi_recommendation/wikidata_collect.py)의 고정 GET/상한/원천 부하 조건, APIerror·정확 ID/revision·허용 필드 검증, 새 snapshot·원자 receipt·실패 보존과 live/offline 구분. 수집 검증이 정체성·권리·학습 품질 승인이 되지 않도록 한다.
- 근거: [실제 원천 관측](WIKIDATA-COLLECTION.md), [계획/검증](plans/2026-11-01-wikidata-collection.md), [실패 경계 회귀](../tests/test_wikidata_collect.py). 신규 accepted0·제품 부재 미확정이며 기존4항목 offline 재생은 새 수집이 아니다. 원문·영수증은 ignored에만 있다.
- 대안/선택: HTTP 상태만 확인하면 간단하지만 source 보류·누락과 정상 empty를 혼동한다. maxlag 완화/즉시 반복보다 실패 상태·이전 snapshot을 보존하고 독립 작업을 계속하는 방식을 선택했다.
- 비교/교체 이유: 이전 REC-CS01은 외부 의존성을 넣지 않는 초기 health 설계다. 새 사례는 실제 외부계약의 오인 조건과 원인을 관측했고 데이터 ID/revision·반영 시점/보존·원천 부하 경계와 실제 실패 거절을 코드로 설명한다. 구현 분량·신규성·테스트 총수가 아닌 원인 근거/상태 난도·실제 동작을 기준으로 한 항목만 교체했다. B0 사례·순서는 보존하고 대표 수2/4를 유지한다.
- 한계: 이번 실카탈로그 확보·SKU 검수·실카탈로그 모델 fit/관련성/최종 평가는 미완료다. 학습 성과·사용자 선호·시간 성능으로 포장하지 않는다. health 계약은 제품 기능으로 유지한다.

## 보관 — REC-CS01 모델 준비와 프로세스 가용성의 분리

아래는 이전 선정 기록이며 현재 README에서는 더 강한 REC-CS05로 교체했다. 구현과 Git 이력은 보존한다.

- 성격: 장애 복구 실적이 아닌 초기 서버의 의존성·진단 경계 설계.
- 구현: [앱 생성·헬스 처리](../src/pubburi_recommendation/main.py)는 DB·모델 다운로드·외부 키 없이 상태와 서비스 이름만 반환한다.
- 계약 확인: [헬스 테스트](../tests/test_health.py)는 외부 자원을 준비하지 않은 상태의 앱 수명 주기와 HTTP 응답을 확인한다.
- 기존 실행 근거: [기본 구성 PR](https://github.com/Pubburi/Recommendation/pull/1)에서 패키지 빌드와 격리 설치·실제 HTTP 계약을 확인했다. [로컬 운영 PR](https://github.com/Pubburi/Recommendation/pull/2)은 통합 실행 포트와 운영 경계를 정리했다.
- 선정 이유: 아직 없는 모델의 상태를 가용성으로 가장하지 않고 API가 보장하는 의미를 제한한 판단을 설명할 수 있다.
- 제약: 추천 readiness, 장애 시 대체 목록, 데이터 신선도, 모델 품질은 보장하지 않는다. 성능 전후 측정도 없다.
- 이번 문서 작업에서는 서버 기동·테스트를 새로 실행하지 않았다. 새로운 실행 근거는 담당 검증·PR에서 기록한다.

### REC-CS02 — 점수 계산보다 먼저 지켜야 할 추천 조건

- 관련 계획: C03 공통 계약, F03 상품 특성, AI01 콘텐츠 기반 모델, R02–R05 추천·유사도·이유·피드백.
- 성격: 첫 실행 가능한 B0의 예방적 계약 설계. 존재하지 않던 과거 모델의 장애 수정으로 주장하지 않는다.
- 구현: [기본순 엔진](../src/pubburi_recommendation/baseline.py), [입력 경계](../src/pubburi_recommendation/request_limits.py), [API 계약](BASELINE-API.md). 필수/제외 조건을 먼저 적용하고 unknown을 해당 조건에 임의 통과시키지 않는다. 이후 ID 정렬·limit을 적용하며 이유는 적용한 필터를 설명한다.
- 실제 근거: [회귀](../tests/test_baseline.py)에서 직접 작성한 가상 상품의 주종/가격/도수·판매/제외 교집합, unknown/0, 후보 부족·입력 순열·상한·오류를 확인한다. [배포 smoke](../scripts/smoke_distribution.py)는 새 wheel의 실제 POST와 중복 ID 422를 확인한다.
- 비교·선정: REC-CS01의 프로세스 진단과 구분되는 추천 입력/결측/선별 순서 문제다. 입력 순서 유지·인기순·필터 완화를 대안으로 비교하고, 근거 없는 순위/조건 완화를 피하는 실제 엔진을 확보했으므로 독립 사례로 추가한다. 최신성이나 테스트 개수로 승격하지 않았다.
- 한계: 원천 감사·B1 학습·실사용자 품질·Backend/웹 통합은 미완료다. 회귀의 가상 카탈로그를 실제 주류 사실·선호 정답·서비스 성능으로 해석하지 않는다.
- 구현·검증·병합 상태는 [작업 기록](plans/2026-10-31-baseline-contract.md)과 실제 PR에서 관리한다.

## 추가 사례 확보 작업

### REC-CS03 — 데이터 부족과 장애를 구분하는 대체 추천

- 관련 계획: R01·R02 신규 사용자, BE05 대체 응답, AI02·AI04 연동·운영.
- 문제 후보: 사용자 행동 부족, 상품 특성 누락, 모델 준비 실패, 추천 서버 지연을 같은 정상 추천으로 표현하는 경우.
- 확보할 구현: 준비 상태와 데이터 조건을 구분하고 Backend와 실패·시간 제한·대체 응답의 책임을 합의한다.
- 완료 근거: 신규 사용자·일부 결측·빈 후보·모델 미준비·지연/실패의 입력과 반환 경로를 실제로 검증한다. 명시적 관심·추정 취향·시연 데이터를 구분한다.
- README 승격 조건: 관측한 실패와 복구 동작, 실제 코드·API 계약·선택한 대안을 확보했을 때. REC-CS01과 겹치면 더 강한 사례로 교체하고 동일 문제를 중복 집계하지 않는다.
- 2026-11-01의 [B1 HTTP 연결](plans/2026-11-01-content-http-contract.md)은 요청별 fit/상태 격리·usable representation과 무정보/OOV·본문 예산을 구현했다. 실제 fixture HTTP/API 경계는 확보했으나 과거 서비스 상태 누출을 고친 실적이나 실제 데이터 품질·Backend 장애 대응 완료는 아니다. 기존보다 강한 독립 서비스 사례로 보기에는 근거가 부족해2/4·순서를 유지하며 이력/코드를 보존한다.

### REC-CS04 — 재현 가능한 평가와 데이터 누수 방지

- 관련 계획: AI03 학습·평가·비교, AI04 버전·재현, 서비스 카탈로그 데이터 준비.
- 문제 후보: 공개 데이터의 사용자·상품 ID를 자체 카탈로그와 혼동하거나 최종 평가 정보를 학습·튜닝에 사용하는 경우.
- 확보할 구현: 출처·라이선스·도메인·ID 대응 관계와 분리 방식을 기록하고, 학습·검증·최종 평가 및 모델·데이터 버전을 관리한다.
- 완료 근거: 같은 후보 집합·분리·seed에서 기준선과 모델을 비교하고 실제 표본 규모·Recall/NDCG 등 선택 지표·한계를 남긴다. 최종 평가를 튜닝에 사용하지 않는 실행 기록을 확보한다.
- README 승격 조건: 재현 가능한 실제 평가와 누수 점검·코드가 준비됐을 때. 공개 데이터 결과를 서비스 사용자 품질로 바꾸지 않는다.
- 2026-10-31의 [원천 감사](plans/2026-10-31-catalog-source-audit.md)는 CC0 entity의 브랜드/SKU·단위·unknown과 명시 검수의 경계를 코드로 확인했다. 실제 B1 학습/분리/평가까지 완료하지 않았으므로 현재 2/4를 유지하고 이 후보를 아직 승격하지 않는다.
- 2026-11-01의 [독립 시나리오 검사](plans/2026-11-01-independent-scenarios.md)는 수동 사실과 응답의 분리·전체 케이스/해시·오류 주입을 구현했다. 현재는 REC-CS02 제약 계약의 검증 확장과 겹치며 실제 카탈로그 모델/분리 평가 증거가 아니므로 새 사례로 중복 집계하지 않고 2/4를 유지한다.
- 2026-11-01의 [B1 실제 fit 모듈](plans/2026-11-01-content-feature-fit.md)은 원자 태그/namespace·unknown 수치 기여·SKU그룹 fit/transform 분리와 실제 TF-IDF/수치 fit을 구현했다. 허구 입력 회귀는 확보했지만 서비스 SKU·독립 관련성·실제 신규상품 분리 평가는 아직 없다. 모델 평가 사례의 완료로 승격하거나 B0 결측 사례와 겹쳐 수를 채우지 않고 기존 2/4와 순서를 보존한다.
- 2026-11-01의 [기존 시드·자산 실감사](plans/2026-11-01-legacy-seed-audit.md)는 80행의 시연 값과 실제 이미지80매핑/해시·개별 근거 미확인·학습 승격0을 실행 가능한 격리 도구로 기록했다. 인벤토리/출처 경계의 근거는 늘었지만 검수 서비스 SKU 확보·사실/권리 해결·실제 학습/분리 평가의 결과가 아직 없으므로 모델 문제 해결 사례로 조기에 승격하지 않고 기존2/4를 보존한다.
- 2026-11-01의 [기본 라벨 유실 수정](plans/2026-11-01-wikidata-default-labels.md)은 정상 복구된 실제 같은6항목·동일revision·비라벨 필드에서 결측3/6→0/6을 확인했다. 원인은 mul-only 기본값을 요청/선택하지 않은 것이고 원천 언어를 보존해 해결했다. 실제 원인과 수치 근거는 확보했지만 기존 REC-CS05와 같은 수집 신뢰성 경계이며 아직 서비스 SKU/특성 연결·추천 결과의 영향은 없다. 더 강한 독립 모델/연동 사례로 보기 어려워 새 세 번째로 나누거나 기존 두 개를 교체하지 않는다. [조건/원값/한계](measurements/2026-11-01-default-labels.md)는 보존하며 최신성·숫자 채우기로 승격하지 않았다.
- 2026-11-01의 [실CC0 상품군 표현 학습](plans/2026-11-01-source-family-fit.md)은 원천 상품군5개에서3fit/2transform·3×5/rank3·관측 수치와 OOV 한계를 실제 실행했다. 동결 사실/분할·출처/영수증 binding과 학습 누수 검사는 확보했지만 변환 결과의 알려진 텍스트는 공통 제조사뿐이다. 추천 관련성·서비스 SKU/연동 결과가 없어 REC-CS04 완료나 더 강한 대표 해결 사례로 조기에 승격하지 않는다. 기존2/4/순서를 보존하고 실제 표현 한계와 [학습 원값](measurements/2026-11-01-source-family-fit.md)을 후속 모델 판단 근거로 남긴다.
- 2026-11-01의 [포장 식별 감사](plans/2026-11-01-package-identity-audit.md)는 실제4항목의 GTIN integrity와 같은 item의 용기/용량/도수 조합1개·브랜드/container 혼합을 검수했다. 원천 조회/바코드 통과를 매핑/학습 승인으로 승격하지 않는 코드와 실제4/4 보류를 확보했다. 새 감사의 malformed quantity 경계도 자체 입력으로 재현해 수정했다. 실제 식별 근거는 늘었지만 REC-CS05 원천 신뢰성·REC-CS04 데이터 경계와 겹치고 독립 서비스 영향/추천 품질까지 확인하지 않았으므로 README2/4와 순서를 보존한다. 부족한 두 사례는 계속 미완료이며 카탈로그/모델·연동에서 실증을 확보한다.
