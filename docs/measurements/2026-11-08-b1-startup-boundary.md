# health 뒤 첫 B1의 준비 경계

로컬 세 서버 인수에서 첫 개인화가 Backend3초 예산을 넘어 UNAVAILABLE을 반환했다. 기본 목록은
별도 명시 선택이다. 기존
`41c01ade2e5ba2885cccdeb1bbbe7c0a692b35cc`의 wheel과 실제 검수6상품 입력을 고정하고,
변경 전에 기준값을 측정했다. 실제 사용자 장애·모델 품질·전체 기동 시간 개선을 주장하지 않는다.

## 조건과 원값

[기계 판독 원값](2026-11-08-b1-startup-boundary.json)에 완료3회씩의 모든 timing과
입력/wheel/lock 해시를 남겼다. 원천 상품/업무 응답·실사용 로그·개인 경로는 포함하지 않는다.
Python3.12.14, macOS/arm64, 고정 runtime-only 의존성, 같은6상품·취향·설명 입력이다.
조정자가 확보한 독립 창에서 직렬 실행하고 OS page cache는 초기화하지 않았다.

각 회차는 기존 배포 검사의 `uv venv`→해시 고정 requirements 설치→wheel `--no-deps` 설치를
그대로 사용했다. **자연 발생 package pyc0을 확인했으며 bytecode를 삭제하지 않았다.**
새 프로세스에서 첫 health 전체 본문까지, 그 뒤 첫 B1 전체 본문까지를 각각 perf_counter_ns로
측정한다. 같은 프로세스에서 같은 요청2회를 더 보낸 뒤 종료하고, 같은 설치/pyc를 유지한 새
프로세스의 첫 요청과 warm2회도 기록했다. 소유한 동적 loopback 소켓만 사용하고 proxy를 끈다.
설치 시간은 startup/request 지표에 섞지 않는다. 타이머 뒤 JSON 결과를 독립 비교한다.

| 새 설치, 각 N=3 | 변경 전 원값 ms | 의존성 준비 후 원값 ms |
|---|---|---|
| 프로세스 시작→health |1216.391 /1052.571 /1003.231|23542.144 /22878.357 /23717.639|
| health 뒤 첫 B1 요청 |22556.430 /22396.230 /22816.431|10.251 /10.554 /10.268|
| 프로세스 시작→첫 B1 완료 |23772.869 /23448.853 /23819.733|23552.447 /22888.965 /23728.023|
| 첫 요청3초 초과 |3/3|0/3|

첫 B1 중앙값은22556.430→10.268ms지만 **준비 비용을 health 앞으로 이동한 결과**다.
health 중앙값은1052.571→23542.144ms, 전체 시작→첫 결과 중앙값은23772.869→23552.447ms다.
전체 초기화가 빨라졌다고 판정하지 않는다. N=3의 분포로 운영 p95/SLO를 추정하지 않는다.
같은 설치 재시작의 첫 요청은786.037ms→6.479ms(중앙값), 같은 프로세스 warm은 모두 수 ms다.
순위·점수·fingerprint·기여/이유의 decoded JSON은 모든 전후/재시작/warm에서 같았다.

최초 진단1회는20초 관측 상한에서 만료돼 완전한 지연/HTTP 결과가 없는 censored 실패로 별도
보존했다. 이후 코드 변경 전에 관측 상한만60초로 고정해 완료3회를 얻었다. 완료 표본의 HTTP는
모두200이며3초 초과는 시간 임계 관측이다. 이를 서비스 HTTP 오류율100%→0%로 쓰지 않는다.
startup 관측 상한은 이동한 준비 비용을 수용하기 위해20→60초로 바꿨고 실제 Backend3초·B0
예산은 바꾸지 않았다. 변경 전 health는 전부1.3초 이내여서 이 관측 상한에 걸리지 않았다.

## 원인 범위와 선택

별도 `python -I -X importtime` 단계 진단1회에서 NumPy867.52ms, sklearn21171.07ms,
TfidfVectorizer858.96ms였다. 첫 nonempty B1의 lazy import가 이 작업을 요청 예산에 넣었다.
추적 오버헤드가 있는 진단이며 OS 네이티브 로드와 bytecode 중 어느 것이 주원인인지는
확정하지 않는다. 같은 venv 재시작은 pyc와 파일/네이티브 경로 캐시가 함께 달라지는 조건이다.

프로젝트 wheel 설치에만 `--compile-bytecode`를 적용한 별도3회는36개 project pyc만
만들었고 첫 B1이22018.37–22841.99ms였다. 프로젝트만 준비하는 방법은 해결하지 못했지만
**전체 runtime 의존성 precompile은 미검증**이므로 기각했다고 쓰지 않는다. 설치 옵션/캐시에
기대지 않는 ASGI lifespan 의존성 준비를 선택했고 별도 배포 파이프라인은 추가하지 않았다.

lifespan은 import만 수행하고 상품/샘플 fit·모델 다운로드·학습 상태 공유를 하지 않는다.
Python 의존성 예외는 종류만 기록하고 health/B0 기동을 보존한다. 이 경우 health는 B1 성공
보장이 아니며 Backend fallback이 필요하다. 네이티브 종료나 끝나지 않는 import까지 예외 격리가
보장하지는 않는다. 정상 cold 준비 약23초는 기존 조정자 readiness60초/로컬 stack180초 창에서
기다리고, 준비 뒤 사용자 추천 예산3초와 B0 예산은 유지한다.
