# Recommendation working guide

- Use Python 3.12, FastAPI and uv. Commit uv.lock; sync with --locked.
- Current contracts are GET /health, POST /v1/recommendations/baseline (untrained B0), POST /v1/recommendations/content (request-local B1 known-catalog representation) and opt-in POST /v1/recommendations/exploration. Follow docs/BASELINE-API.md, docs/CONTENT-API.md and docs/EXPLORATION-API.md. The HTTP service loads/persists no startup catalog/model. Separate explicit source-backed business-DEMO fit is documented in docs/REVIEWED-CATALOG-FIT.md; full catalog/relevance/generalization and Backend B1 integration remain incomplete.
- Keep initialization free of database, model download and external API requirements.
- All recommendation POSTs enforce 512 KiB cumulative raw bodies and a total ten-second receive deadline. Keep schema/startup imports free of NumPy/sklearn; load the numerical engine only inside nonempty B1 requests. Preserve existing B0/health and do not claim body timeout cancels or bounds a running CPU fit.
- exploration reuses existing B1 scores/contributions, reranking only its positive/floor-passing top100 pool with one item per reviewed sku_group. Keep hard/exclusion/floor bounds, conservative unknown text penalty and separate MMR selection metadata; do not label missing facts as novel styles or fill shortages. This is an opt-in R08 technical increment, not complete R08/Backend/web integration or user-quality evidence.
- After receiving a bounded JSON body, reject duplicate decoded object keys with fixed 422 duplicate_json_key diagnostics before schema/ranking/fit only after the entire JSON decode succeeds. Track duplication per request without raising inside the object hook: later syntax/encoding/depth failures must retain the framework's original priority. Include escaped-equivalent names and identical duplicate values; names repeated in different objects remain valid. Match application/json, application/*+json and absent-content-type JSON handling. Keep numeric/schema errors on the existing framework path; the extra decoder pass is not a CPU deadline or a performance improvement.
- Offline source preparation uses python -m pubburi_recommendation.catalog_audit and docs/CATALOG-AUDIT.md. Source manifests record reviewed scope, not automatic legal approval. Keep raw/normalized catalogs in ignored .pubburi only; entity/brand IDs must never become Backend SKU IDs without explicit review.
- Explicit small Wikidata acquisition/replay uses python -m pubburi_recommendation.wikidata_collect and docs/WIKIDATA-COLLECTION.md. Keep fixed HTTPS/single GET/maxlag5/10-ID/byte/timeout gates; never treat HTTP200 API errors as empty or accepted catalogs. Respect maxlag/rate limits without threshold bypass. Require accepted receipt + exact IDs/revisions before use; offline replay is not new acquisition, collection acceptance is not SKU/quality/training approval.
- Request structured labels in ko/en/mul and preserve ko → en → mul precedence with label_language. mul is a source default label, not inferred Korean/English or a translated name. Missing labels stay unknown; never derive them from descriptions, aliases or IDs. A changed raw snapshot requires its own hash-bound review; normalization provenance must be rechecked before reuse.
- Legacy seed/media inventory uses python -m pubburi_recommendation.legacy_seed_audit and docs/LEGACY-SEED-AUDIT.md. Never execute seed SQL, export user/password rows, infer SKU/volume/taste from names or treat demo prices/order counts as observations. Existing project provenance does not grant per-record/media rights; current legacy outputs stay quarantined and cannot automatically approve training/public reuse.
- Source package evidence uses python -m pubburi_recommendation.package_identity_audit and docs/PACKAGE-IDENTITY-AUDIT.md. Bind accepted source receipt/raw/manifest and manual review/revision; preserve GTIN strings/unknown quantities and hold mixed brand/container grain or shared identifiers. Check digits and same-item package fields are not GS1 assignment/authenticity, sale/SKU approval, Backend mapping or fit eligibility. Keep catalog/receipts/reviews private; never infer packaging/pack count or use this audit as an automatic training gate.
- volume_context preserves explicitly reviewed P2234/P518 statement observations separately from family scalar volume; follow docs/VOLUME-CONTEXT.md. Bind both source/definition receipts and frozen facts, preserve one family group across contexts, and hold duplicate/conflicting/ambiguous quantities instead of averaging or collapsing. Context definitions and volume observations are not complete physical packages, SKU/Backend mappings or fit approval; never infer missing GTIN/ABV/pack count/price.
- Explicit source-container curation uses python -m pubburi_recommendation.source_catalog and docs/SOURCE-CATALOG.md. Its fields come only from allowed CC0 raw/revision; external first-party links are human identity cross-check notes, never text/image/taste/price datasets or a new rights grant. Preserve original types/holds, require scoped mixed-type interpretation, and never override collisions/unknown. String source catalog IDs/variant groups are not Backend IDs; this curation CLI itself provides no business mapping/export.
- Reviewed offline demo export uses python -m pubburi_recommendation.business_export and docs/BUSINESS-EXPORT.md. Recompute source authorities; bind explicit one-to-one IDs/groups/whole-response and snapshot hashes, preserve quantities/unknown and demo-price authority, and reject stale/future/changed/mismatched inputs or fixture/public origin mixing. Hashes/capture times are not provider revisions or atomic/live sale checks. Never infer IDs or rights from names/sourceName/URLs. No mapping means no request files. Real licensed service mapping/fit/quality remain incomplete; owned/authored DEMO flows are contract evidence only.
- reviewed_catalog_fit executes the existing B1 model on that reviewed mapping and compares B0 under a pre-fit frozen factual spec. Verify facts before fit, inspect results without production filter/scoring helpers, and keep parameters/results private. Actual source-backed business-DEMO currently has one product/group, one business-category token and inactive constant quantity scales: actual known-catalog fit is not ranking quality, user learning, held-out generalization or full AI03 completion. Existing_local_catalog may represent real source facts in a disposable business DEMO with explicit demo prices; it never proves sale/stock.
- Follow docs/EVALUATION.md for frozen authored scenarios and the independent result checker. Production scoring/filter helpers must not generate expected labels. B0 ID order is not B1 relevance truth; fixture checks do not establish user preference quality or final model evaluation.
- B1 fit/rank is implemented in content_model; follow docs/CONTENT-MODEL.md. Offline generalization experiments fit training SKU groups only and transform never refits. HTTP content fits each explicit request catalog locally: this is known-catalog representation, not held-out/user learning. Keep atomic tags, unknown masks, real contributions and deterministic fallback. Empty/uninformative catalogs never claim a usable fitted representation. content_experiment accepts authored fixtures only; service SKU fit/quality and Backend B1 integration remain incomplete.
- source_family_experiment is a separate offline representation/partition audit for explicitly reviewed CC0 source product families. Follow docs/SOURCE-FAMILY-EXPERIMENT.md: bind source/review/receipt/manifest/spec hashes and frozen facts/groups, fit training families only, preserve unknown/OOV, and keep model parameters private. Source QIDs never become Backend IDs, these families are not packaging SKUs, and real source-family fit is not service B1 fit or recommendation relevance quality. No duplicate service ranker or HTTP integration is provided.
- Optional frozen source-family retrieval cases compare transformed queries with fit-only candidates using existing TF-IDF text representations. The independent inspector applies manually declared exact-P31 fact judgments; this shared-feature relation is not independent human preference truth. Keep complete rankings, positive/zero-label query denominators and no-positive metric omissions. The lexical source-ID reference is separate from Backend/service B0; do not tune on held-out queries or claim tiny fact retrieval metrics establish service quality.
- source_family_cohort reuses separately accepted/reviewed snapshots for an explicit unseen-producer split; follow docs/SOURCE-FAMILY-COHORT.md. Preserve each raw/receipt/review/manifest hash and selected revision, reject overlapping selected source IDs instead of merging/overwriting, and verify unqualified P31/P176 source relationships. Family groups are curator declarations, not physical SKU identity proofs. Reuse existing fit/evaluator and report zero-vector coverage beside positive-query metrics; never synthesize a collection receipt or auto-promote a cohort to business IDs/quality.
- Validate with ./scripts/check.sh (pytest, Ruff and distribution build).
- Implement data preparation, content-based recommendations, fallbacks and model evaluation under the approved roadmap; never present unfinished features as implemented.
- Do not commit datasets, model weights, .venv/, credentials or generated distributions.
- Use PRs and Conventional Commits. Mobile implementation is separately owned.

## 커밋·PR 작성

- [협업 규칙](CONTRIBUTING.md)에 따라 `feat:`, `fix:`, `test:`, `ci:`, `docs:` 등의 영어 유형과 한국어 제목·필요한 본문을 사용한다. 식별자·제품 이름은 원문을 유지할 수 있다.
- 한 커밋은 한 가지 검토 가능한 목적을 담고 필요한 구현·테스트·문서를 함께 묶는다. 무관한 모델/데이터·리팩터링·의존성 변경은 분리하며 각 커밋을 빌드·검증 가능한 상태로 유지한다. WIP·빈 커밋·파일별 억지 분할은 하지 않는다.
- PR 제목과 최종 Squash 제목도 한국어 Conventional Commit 형식으로, 필요한 Squash 본문도 한국어로 작성한다. 기존 Squash 방식을 유지하며 main의 독립 변경 단위는 PR부터 나눈다. 과거 병합 이력은 재작성하지 않는다.
